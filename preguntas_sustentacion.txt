 12. FORMULARIOS HTML Y VALIDACION DE DATOS
--------------------------------------------------------------------------------

P: Si en un campo que es int/float (ej. la cuota) el usuario escribe un string
   o un numero invalido, tu funcion de FastAPI revienta? Quien controla eso?

R: NO revienta, y no lo controla mi funcion: lo controla FastAPI/Pydantic
   AUTOMATICAMENTE y ANTES de que mi codigo corra. Es validacion en la "puerta".

   El orden real cuando llega cuota="hola":
     1. FastAPI/Pydantic revisa los tipos primero ("hola" no es float).
     2. Rechaza con error 422 automatico.
     3. Mi funcion NUNCA se ejecuta (el commit, el Crear_..._bd, nada corre).

   La validacion vive en la FIRMA de la funcion:
       async def crear_pierna_post(cuota: float = Form(), ...):
   Ese ": float" ES la validacion. Si mandan texto -> 422 solo, sin escribir nada.
   Tambien valida rangos definidos en el modelo (ej. prob con ge=0, le=1) -> 422.

   Por eso NO pongo un "if type(cuota)!=float: raise": seria codigo muerto, nunca
   se cumpliria porque el 422 ya freno la peticion antes.

   Diferencia clave 422 vs 404 (me pueden corchar con esto):
     - 422 = datos MAL FORMADOS (string en int, fuera de rango, campo faltante).
             -> Lo lanza FastAPI SOLO, automatico.
     - 404 = el dato es VALIDO pero NO EXISTE el recurso (ej. borrar pierna #999).
             -> Lo lanzo YO a mano con raise HTTPException(404).
     - 400 = peticion valida en tipos pero que la logica/BD no pudo procesar
             (ej. la BD de Neon se cayo al guardar) -> lo lanzo yo.

   Resumen de una frase:
     Datos mal escritos -> 422 automatico, antes de mi funcion.
     Datos validos que la BD/logica no puede procesar -> ahi va mi raise HTTPException.

   Mi app tiene las DOS capas: validacion automatica (tipos/rangos) en front+back,
   y manual (404/400) para la logica de negocio. Eso es lo "robusto front y back".

--- Sobre la validacion FRONTEND (lo que agregue en los formularios) ---

P: Que es "step" en un input numerico?
R: Es el tamano del salto del numero, y de paso controla cuantos decimales se
   permiten. step="0.01" -> acepta hasta 2 decimales (1.85). step="1" -> solo
   enteros. step="any" -> cualquier cantidad de decimales. Tambien es cuanto
   suben/bajan las flechitas del input.

P: Que validaciones le pusiste al frontend?
R: En los <input>: type="number" (solo numeros), required (obligatorio),
   min/max (rango, ej. cuota min=1.01, prob min=0 max=1), step (decimales),
   maxlength (tope de caracteres en texto). Asi el NAVEGADOR avisa antes de
   enviar. Ademas estado y activo pasaron de texto libre a <select> para que
   solo se puedan elegir valores validos del enum.

--- Sobre la RETROALIMENTACION de errores (mostrar bonito en HTML) ---

P: Como muestras los errores? Sale el JSON crudo de FastAPI?
R: No. En los formularios (crear combinada / crear pierna) cuando algo esta mal
   RE-MUESTRO el mismo formulario con una alerta roja de Bootstrap arriba
   (<div class="alert alert-danger">) y CONSERVO lo que el usuario ya escribio
   (precargo los <input> con value="{{ valores.x }}"). Asi no pierde el trabajo
   y entiende que corregir.

P: Por que en los formularios cambiaste los campos de "float" a "str" en la firma?
R: A proposito, para poder controlar yo el error y mostrarlo bonito.
   - Si dejo "cuota: float", FastAPI lanza el 422 AUTOMATICO antes de mi codigo y
     el usuario ve el JSON feo; mi funcion no alcanza a re-mostrar el formulario.
   - Al recibir "cuota: str" y convertir yo con float() dentro de un try/except,
     SI puedo atrapar el error y devolver el formulario con un mensaje amable.
   Es un intercambio consciente: cambio el 422 automatico por validacion manual
   para ganar control sobre la retroalimentacion. Igual sigo validando rango
   (cuota>1, prob entre 0 y 1) y el FRONTEND tambien valida (doble capa).

P: Y la API (POST /Combinada con JSON) sigue validando tipos sola?
R: Si. Ese endpoint NO es de formulario: recibe un CombinadaBase (Pydantic), asi
   que ahi el 422 automatico sigue funcionando. El cambio a str solo lo hice en
   los endpoints de FORMULARIO HTML, que son los que devuelven pagina.

P: Cuando hay error, sale un popup/ventanita?
R: No. NO es un popup de JavaScript. Re-renderizo (vuelvo a dibujar) la PAGINA
   ENTERA del formulario con TemplateResponse, pero esta vez con una alerta roja
   arriba ({% if error %}). El usuario se queda en la misma URL /Pierna/Crear/
   (no hay redirect) y ve la pagina recargada completa, con lo que ya habia
   escrito precargado en los inputs (value="{{ valores.x }}").

P: En volver_con_error, por que vuelves a consultar Mostrar_Combinadas_bd si solo
   querias mostrar un error?
R: Porque re-dibujo TODA la pagina, y esa pagina tiene un <select> que se llena
   recorriendo la lista de combinadas ({% for c in combinadas_lista %}). Jinja no
   "recuerda" los datos de la vez anterior: cada vez que renderizo una plantilla
   tengo que pasarle TODOS los datos que necesita. Si no le paso combinadas_lista,
   el <select> saldria vacio. Por eso la vista GET y la funcion de error pasan las
   dos la misma lista; la de error solo agrega ademas "error" y "valores".

P: Si el frontend se puede saltar, donde queda la validacion REAL? Valida el HTML
   o valida FastAPI?
R: Validan los dos, EN CASCADA: primero el HTML (navegador), y si se lo saltan,
   valida FastAPI = mi codigo en main.py. La validacion real (la que no se puede
   esquivar) esta en el backend.
   Capas de mi app:
     1. Frontend (HTML/navegador): required, min, max, step. Avisa antes de enviar
        pero es SALTABLE (DevTools, curl, novalidate).
     2. main.py (mi codigo Python): el try/except float() y los if de rango. ESTA
        es la que atrapa el dato malo si se saltan el front, y re-renderiza el form
        con mensaje bonito.
     3. Modelo Pydantic (Modelos.py): las reglas Field(ge=1, le=1...) se revisan al
        construir el objeto (PiernaBase(...)). Ultima red.

   SUTILEZA IMPORTANTE (por el cambio a str): en los formularios los campos son
   "str" (ej. cuota: str = Form()). Eso significa que FastAPI ya NO rechaza solo
   los numeros malos en el form (str acepta "hola"); quien valida es MI codigo en
   main.py con float()/try-except. Apague el 422 automatico a proposito para poder
   mostrar el error bonito. En la API JSON (POST /Combinada con CombinadaBase) si
   sigue el 422 automatico de Pydantic, porque ahi NO use str.

P: Que hace -> cid = int(combinada_id) if combinada_id else None
R: Es un if en una linea (ternario). Todo lo que viene de un form llega como TEXTO
   (string). El <select> manda "" si eligio "sin combinada", o "3" si eligio una.
   - Si combinada_id tiene texto ("3") -> int() lo convierte a numero 3 (la FK del
     modelo es int).
   - Si esta vacio ("") -> en Python "" es falsy, asi que el if da falso y asigna
     None = pierna "libre" (va al pool para arrastrar).
   El if va PRIMERO para protegerme: int("") reventaria con ValueError.
